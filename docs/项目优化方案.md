# 项目优化方案（v1）

> 对象：AI 视频翻译系统（`video-translation`）
> 前提：前端已完成「字幕工作台」重构；本文针对**功能缺口与工程质量**，给出可按期验收的优化路线。

---

## 1. 结论先行

前端已经从「能用」走到「好看」，但产品链路还停在「一次请求 = 一次翻译」：

- **没有任务概念**：没有 jobId，进度是全局广播，刷新即失忆；
- **数据库空转**：`jobs / job_steps / translations / voice_sessions / voice_lines` 五张表已建，但后端一行代码都没接；
- **演示脆弱**：没有外部 API Key 或断网时，整条链路无法演示；
- **工程欠账**：0 个测试、无 API 文档、`server.js` 80KB 单文件、上传无大小限制。

所以优化的主线不是「再加页面」，而是**把一次性的翻译请求，变成可追踪、可恢复、可演示的任务系统**。

---

## 2. 现状盘点

### 2.1 已具备

| 能力 | 位置 | 说明 |
|---|---|---|
| 任务队列 | `server.js` `TaskQueue` | 默认并发 2，按 CPU/内存动态调整 1–4 |
| 长视频分段 | `server.js` | >5 分钟自动切段，逐段 ASR → 翻译 → 合成 |
| 进度推送 | `/ws/progress` | 服务端主动推送 step + progress |
| 运行监控 | `MonitoringSystem` | 请求数、成功率、平均耗时（仅内存） |
| 文件清理 | 24h / 1GB 阈值 | 临时目录自动回收 |
| 语音实时翻译 | `voice-translation.js` + `/ws/voice-translation` | 本地 Sherpa-ONNX + 火山/混元双后端 |
| 前端工作台 | `src/App.jsx`、`VideoStudio.jsx` | 设计令牌、双主题、三栏布局、响应式 |

### 2.2 缺口（按严重度）

| 编号 | 问题 | 证据 | 影响 |
|---|---|---|---|
| P0-1 | 进度全局广播 | `const clients = new Set()`，`/ws/progress` 无 jobId | 多人/多标签页同时使用会串台，A 的进度显示在 B 的界面 |
| P0-2 | 无任务标识与持久化 | `POST /api/translate-video` 同步等待，`res.json(result)` 一次返回 | 刷新丢失、失败无重试、无法查历史 |
| P0-3 | 上传无限制 | `multer({ storage })` 未设 `limits` | 超大文件可打满磁盘，属于可用性风险 |
| P0-4 | 数据库未接入 | 表已建，代码 0 引用 | 数据资产无法沉淀，ER 图与实现脱节 |
| P1-1 | 无历史/重试/取消 | 前端无入口，后端无接口 | 用户每次都要重新上传，体验断裂 |
| P1-2 | 无 Mock 模式 | 无假数据管线 | 答辩现场无网/无 Key 直接失效 |
| P1-3 | 语音页风格不一致 | `VoiceTranslation.css` 681 行硬编码金色 | 产品观感割裂，且记录只存内存 |
| P1-4 | 无 API 文档 | 仅 `开发文档.md` 叙述 | 前后端协作与论文写作都缺依据 |
| P2-1 | 无测试 | 前后端均无 `.test` 文件 | 重构与接库没有安全网 |
| P2-2 | 单文件巨石 | `backend/server.js` 约 80KB | 维护成本高，问题定位慢 |
| P2-3 | 错误无码 | 前端只拿到字符串 | 无法区分「用户错误 / 上游失败 / 系统错误」 |
| P2-4 | 监控不持久 | 内存统计 | 重启清零，无法做趋势 |
| P2-5 | 半成品功能 | 字幕样式、翻译校准 UI 已撤、后端参数仍在 | 代码与界面不一致 |

## 3. 目标与验收指标

| 目标 | 可验收指标 |
|---|---|
| 任务可追踪 | 每次翻译返回 `jobId`；进度消息携带 `jobId`；刷新后可恢复；历史列表可查 |
| 多任务互不干扰 | 两个浏览器标签同时跑任务，进度各自独立，无串台 |
| 演示自洽 | 无外部 Key、断网状态下可完整跑通「上传 → 进度 → 结果 → 下载」 |
| 工程可维护 | `server.js` 拆分后单文件 < 300 行；核心链路有测试；API 有文档 |
| 论文可用 | ER 图、架构图、时序图与代码一致，可直接进论文 |

---

## 4. 分阶段路线

### Phase 1 · 任务化与历史（P0，优先级最高）

**后端**

1. 生成 `jobId`（`crypto.randomUUID()`），先落 `jobs`（status=pending），再进入队列；
2. 状态机：`pending → running → succeeded | failed | canceled`，每次变更写 `jobs.updated_at`；
3. 每一步写 `job_steps`，翻译句对写 `translations`；
4. 进度协议改为 `{ type: 'progress', jobId, step, progress }`；WebSocket 支持按 job 订阅（连接参数或首帧 `subscribe`）；
5. 新增接口：
   - `GET /api/jobs`（分页，倒序）
   - `GET /api/jobs/:id`（含步骤与产物地址）
   - `POST /api/jobs/:id/cancel`
   - `POST /api/jobs/:id/retry`
6. `multer` 增加 `limits: { fileSize: 2GB, files: 1 }` 与 MIME 白名单。

**前端**

1. 提交后立即拿到 `jobId`，进度按 `jobId` 过滤；
2. 新增「历史」抽屉：任务卡片（文件名、语言对、状态、耗时、大小），支持重新下载与重试；
3. 断线重连后按 `jobId` 拉一次 `GET /api/jobs/:id` 对齐状态；
4. 失败态给出可操作按钮（重试 / 换文件 / 查看日志）。

**验收**：两个标签页并行不串台；刷新页面历史仍在；上传 3GB 文件被明确拒绝。

### Phase 2 · 演示与体验（P1）

1. **Mock 管线**：抽出 `asr / translate / render` 三个 provider 接口，Mock 实现 3 秒内走完全流程并返回示例字幕；
   - 开关：后端 `PIPELINE=mock`，或前端 `?mock=1` 仅前端模拟；
2. **示例素材**：内置 15 秒样片与中英字幕，一键「试跑示例」；
3. **字幕编辑器**：结果页可编辑 SRT 行（原文/译文/时间码），保存后重新合成；
4. **语音页统一**：把 `VoiceTranslation` 迁到工作台设计令牌，历史记录落 `voice_sessions / voice_lines`；
5. **状态完整性**：骨架屏、空态插画、错误码文案映射、无障碍复查。

**验收**：拔网线、清空 `.env`，仍能完成演示；语音页与视频页视觉一致。

### Phase 3 · 工程化（P2）

1. 拆分 `server.js`：`routes/`、`services/`、`pipeline/`、`ws/`，先加冒烟测试再动手；
2. 统一错误码（`E_UPLOAD_TOO_LARGE`、`E_UPSTREAM_TIMEOUT`…），前端集中映射；
3. 结构化日志（请求 id + jobId + 耗时）；
4. 测试：`vitest` + `supertest` 覆盖任务状态机、队列并发、SRT 解析、上传校验；前端 `@testing-library/react` 覆盖工作台主流程；
5. CI：GitHub Actions 跑 lint + test + build（配合已有的推送前安全审查）；
6. OpenAPI 文档（`openapi.yaml`）+ README 重写。

**验收**：`npm test` 全绿；CI 在 PR 上通过；新同学按 README 30 分钟内跑起来。

### Phase 4 · 论文与答辩材料

1. ER 图（与 `schema.sql` 一致）、系统架构图、视频翻译时序图、实时语音时序图、用例图；
2. 性能数据：并发 1/2/4 下的平均耗时、成功率、资源占用（用现有监控埋点采集）；
3. 演示脚本：3 分钟标准流程（示例素材 → 进度 → 编辑字幕 → 历史回看）。

---

## 5. 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 任务标识 | `jobId` + 数据库状态机 | 同时解决串台、刷新丢失、历史三个问题 |
| 进度通道 | 保留 WebSocket，消息带 `jobId` | 改动最小，兼容现有前端逻辑 |
| 数据库 | 继续 SQLite（已建表），保留 MySQL 迁移路径 | 零运维、答辩稳定；schema 未用方言特性 |
| Mock 位置 | 后端 provider 层，而非前端假数据 | 一套开关同时服务演示与自动化测试 |
| 拆分顺序 | 先 `pipeline`/`ws`，后 `routes`，最后 `services` | 风险从低到高，每步可回归 |
| 用户系统 | 暂不做（单用户本地部署） | 需求文档未要求，避免范围膨胀 |

---

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 80KB 单文件重构引入回归 | 高 | 先补冒烟测试与 3 条黄金路径，再逐块搬 |
| 外部 API 不稳定 | 中 | 超时 + 重试 + Mock 垫底 |
| SQLite 并发写 | 低 | WAL 模式（已启用）+ 单写队列 |
| 答辩时间紧 | 高 | Phase 1/2 必做，Phase 3 可裁剪到「测试 + README」 |
| 历史数据与旧接口不兼容 | 中 | 新旧接口并存一个版本，前端灰度切换 |

| 顺序 | 内容 | 预估 | 依赖 |

| 1 | Phase 1 后端任务化（jobId、落库、接口、上传限制） | 1.5–2 天 | 无 |

---

## 8. 本方案明确不做

- 用户注册/登录/多租户（需求未要求，收益低）；
- 微服务化、消息队列中间件（本地部署场景过度设计）；
- 前端换框架或上 SSR（现有 Vite + React 已满足）；
- 自动字幕翻译质量评估模型（工作量与答辩收益不匹配，可写进「未来工作」）。
